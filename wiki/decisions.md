# Architecture Decisions

## ADR-1: Separate AI Microservice

**What:** AI features are implemented as a standalone FastAPI service (`ai-service/`) that the backend calls via HTTP, rather than running LLM logic inside the backend.

**Why:** LLM dependencies (SDKs, model loading) are heavy and change frequently. Isolating them prevents the main backend from becoming unstable or bloated. The AI service can be independently deployed, scaled, and swapped between mock and live modes without touching the core API.

**Tradeoffs:**
- ✅ Independent deployment and scaling
- ✅ Mock mode for development (no API keys needed)
- ✅ Backend controls access (frontend never calls AI directly)
- ❌ Extra network hop for AI requests (+latency)
- ❌ Another service to monitor and maintain

**Alternatives Considered:**
- **LLM calls in backend service layer** — simpler but couples LLM churn to core API stability
- **Frontend calls LLM directly** — exposes API keys to client, no server-side rate control

## ADR-2: Multi-Tenant Organizations from Day 1

**What:** Users belong to organizations, and all projects are scoped to an organization. A personal org is auto-created on registration.

**Why:** The university project requires multi-tenancy ("users can be part of a company or group"). Building this before task CRUD ensures every feature is multi-tenant from the start. Adding multi-tenancy retroactively would require migrating every query, endpoint, and permission check.

**Tradeoffs:**
- ✅ Data isolation guaranteed from the start
- ✅ No costly refactoring later
- ✅ Org switcher for users with multiple orgs
- ❌ Week 2.5 added to timeline (complexity for MVP)
- ❌ Personal org auto-creation adds an implicit convention

**Alternatives Considered:**
- **Add multi-tenancy in V1.1** — cheaper now, exponentially more expensive later
- **Workspace-based** — too generic, "organization" better maps to PM domain

## ADR-3: Cookie-Based JWT Authentication

**What:** Access and refresh tokens are delivered as HTTP-only, secure cookies with path scoping, rather than returned in JSON and stored in localStorage.

**Why:** HTTP-only cookies are immune to XSS — JavaScript cannot read them. Path scoping (access token on `/api`, refresh token on `/api/v1/auth`) ensures the refresh token is only sent to auth endpoints, reducing attack surface.

**Tradeoffs:**
- ✅ XSS-immune token storage
- ✅ Refresh token never sent to non-auth endpoints
- ✅ Browser handles sending automatically
- ❌ CSRF considerations (mitigated by SameSite cookies)
- ❌ Slightly more complex than localStorage approach

**Alternatives Considered:**
- **localStorage** — vulnerable to XSS attacks
- **sessionStorage** — lost on tab close, bad UX
- **In-memory only** — lost on page refresh

## ADR-4: Feature-Sliced Frontend Architecture

**What:** Frontend is organized by feature domain (auth, projects, tasks, gantt, etc.), not by file type (pages/, hooks/, services/). Each feature is a self-contained module with barrel exports.

**Why:** As the app grows to 11+ features with complex interactions, a file-type organization (all hooks in one folder, all services in another) creates coupling and makes it hard to find related code. Feature slicing keeps related code together and enforces module boundaries.

**Tradeoffs:**
- ✅ Related code lives together (easy to find)
- ✅ Clear ownership boundaries per feature
- ✅ Easy to add/remove features
- ✅ Barrel exports prevent internal coupling
- ❌ Some duplication vs shared utilities (mitigated by `shared/`)
- ❌ Must enforce the rule that `shared/` only contains truly shared code

**Alternatives Considered:**
- **File-type organization** — simpler at small scale, collapses at 10+ features
- **Atomic Design** — good for component libraries, not for business features

## ADR-5: UUIDv7 for All Primary Keys

**What:** All tables use UUIDv7 (time-ordered UUID) as primary keys, generated by `uuid_generate_v7()` in PostgreSQL.

**Why:** UUIDv7 combines the benefits of UUIDs (globally unique, no coordination needed) with natural time ordering for better B-tree index performance. Standard UUIDv4 causes random insertions that fragment indexes; v7 inserts in order like auto-incrementing integers but without the downsides (enumeration attacks, cross-service conflicts).

**Tradeoffs:**
- ✅ Globally unique without coordination
- ✅ Time-ordered for optimal index performance
- ✅ No enumeration attacks (unlike sequential integers)
- ❌ Larger than INT (16 bytes vs 4 bytes)
- ❌ Requires `pg_uuidv7` PostgreSQL extension
- ❌ Verbose in URLs and logs

**Alternatives Considered:**
- **Auto-increment INT** — enumerable, coordination problems across services
- **UUIDv4** — random inserts fragment B-tree indexes, poor write performance at scale
- **ULID** — similar benefits but less PostgreSQL ecosystem support

## ADR-6: Plain Functions for Backend Services (No Classes)

**What:** All backend service layer code uses plain `async` functions, not service classes with methods.

**Why:** Service classes in Python often become god objects with implicit state. Plain functions are simpler, easier to test (no instantiation), and naturally compose. FastAPI's dependency injection works with functions directly — no factory patterns or singletons needed.

**Tradeoffs:**
- ✅ Simpler, more readable code
- ✅ Easier to test (import and call)
- ✅ No hidden state or initialization
- ✅ Works naturally with FastAPI DI
- ❌ Cannot inherit shared behavior (mitigated by composition)
- ❌ Long parameter lists on some functions

**Alternatives Considered:**
- **Service classes** — traditional OOP pattern, but leads to god objects in Python backend code
- **Use-case classes** — adds ceremony without proportional benefit at this scale

## ADR-7: Strict Backend Layer Direction (API → Service → Repository)

**What:** The backend enforces a unidirectional dependency flow: `API → Service → Repository → Models`. Services must not import API schemas. Repositories must not import services or API code.

**Why:** Without layer enforcement, the codebase quickly becomes a web of circular dependencies. Services importing API schemas couples business logic to HTTP contract details. The clean separation makes each layer independently testable and refactorable.

**Tradeoffs:**
- ✅ Each layer is independently testable
- ✅ Prevents circular dependency chains
- ✅ API schema changes don't ripple into business logic
- ❌ Services sometimes need to duplicate transformation logic
- ❌ Requires service-level contracts (`service/contracts/`) as bridge types

**Alternatives Considered:**
- **Two-layer (API → DB)** — simpler but business logic leaks into endpoints
- **No enforcement** — works at 5 endpoints, collapses at 75+

## ADR-8: Soft Deletes with Partial Indexes

**What:** Projects, tasks, organizations, and comments use soft deletes (`is_deleted` + `deleted_at` columns) instead of `DELETE FROM`. All query indexes use `WHERE NOT is_deleted` partial indexes.

**Why:** Hard deletes in a PM tool are dangerous — users may accidentally delete a project with months of work. Soft deletes allow recovery and audit trails. Partial indexes ensure queries only scan active records, maintaining performance.

**Tradeoffs:**
- ✅ Data recovery possible (undo delete)
- ✅ Audit trail preserved
- ✅ Partial indexes keep queries fast
- ✅ Cascading soft-delete to child tasks
- ❌ Every query must filter `is_deleted=False` (handled by repository layer)
- ❌ Storage grows over time (mitigated by eventual purge jobs)

**Alternatives Considered:**
- **Hard deletes** — simpler but irreversible, risky in a PM context
- **Archive table** — adds complexity with `INSERT INTO archive + DELETE FROM main`
- **Event sourcing** — overkill for this application's needs
